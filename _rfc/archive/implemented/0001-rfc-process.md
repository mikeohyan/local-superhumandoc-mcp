# RFC 0001 — Record design decisions as immutable RFCs in `_rfc/`

## Context

This repository is built almost entirely through Claude Code sessions. A
session's reasoning — the options weighed, the constraint that ruled one out,
the assumption a choice rests on — lives in a transcript that the next session
cannot read. Without a durable record, each new session re-derives decisions
from the code alone, re-proposes alternatives that were already rejected, and
silently contradicts choices whose rationale it never saw.

The Superpowers plugin already produces most of the raw material. Its
`brainstorming` skill forces 2–3 approaches with trade-offs and writes a design
document; `writing-plans` produces an implementation plan; `verification-before-
completion` gates the claim that work is done. What is missing is not more
process but a stable, discoverable home for the output, plus a rule for what
happens when a decision is later reversed.

The constraint that shapes everything below: the primary reader is a Claude Code
session with no memory of how these files came to exist. It must be able to find
the current decisions, tell them apart from the retired ones, and know without
ambiguity whether it is allowed to edit a given file.

## Decision

Design decisions are recorded as numbered RFCs under `_rfc/`. An RFC is written
before the work it describes, approved by the repository owner, and frozen once
approved. Decisions are never rewritten; they are superseded by later RFCs.

### Layout

```
_rfc/
  README.md                         index of every RFC, generated by the rfc skill
  TEMPLATE.md                       the canonical RFC skeleton
  0002-slug.md                      Proposed or Accepted: decided, not yet shipped
  plans/
    0002-plan.md                    mutable implementation plan, checkboxes and all
  archive/
    implemented/0001-slug.md        shipped, and still the current truth
    retired/0003-slug.md            Superseded or Rejected: no longer true
```

A given RFC number therefore lives in one of three directories depending on its
status. Nothing may hardcode an RFC's path; the lookup is
`ls _rfc/NNNN-*.md _rfc/archive/*/NNNN-*.md 2>/dev/null`, or `_rfc/README.md`, which records each RFC's location.

The second archive is named `retired/` rather than `superseded/` so that
Rejected RFCs — decisions that were never true, as opposed to decisions that
stopped being true — have an honest home.

### Frontmatter and body

Every RFC carries the YAML frontmatter and section headings defined in
`_rfc/TEMPLATE.md`: Context, Decision, Alternatives considered, Consequences,
Implementation notes. `TEMPLATE.md` is the single source of truth for that
shape; the `rfc` skill points at it rather than restating it.

**The body freezes at Accepted. The frontmatter stays living.** This split is
what makes immutability a rule that can actually be followed: `status`,
`decided`, `superseded_by`, and `commits` must keep changing after approval,
while prose that has been approved must not be quietly rewritten. The one
exception is Implementation notes, which the shipping session fills in — it
records what happened, and so cannot be written before it happens.

### Numbering

Four digits, zero-padded, allocated in order across all three directories:

```bash
ls _rfc/[0-9]*.md _rfc/archive/*/[0-9]*.md 2>/dev/null \
  | grep -oE '[0-9]{4}' | sort -n | tail -1
```

### Lifecycle

| Transition | Trigger | Action |
|---|---|---|
| → Proposed | `brainstorming` reaches "write design doc" | write `_rfc/NNNN-slug.md`, commit |
| → Accepted | owner approves at the spec-review gate | set `status`, `decided`; update index |
| plan created | `writing-plans` runs | write `_rfc/plans/NNNN-plan.md` |
| → Implemented | `verification-before-completion` passes | record `commits`, fill Implementation notes, `git mv` to `archive/implemented/`, `git rm` the plan; update index |
| → Rejected | owner declines at the spec-review gate | set `status`, `git mv` to `archive/retired/`; update index |
| → Superseded | a later RFC declares `supersedes: N` | set `superseded_by`, `git mv` to `archive/retired/`; update index |

Every file relocation uses `git mv`, never a plain `mv`. A plain move registers
as an untracked addition plus a deletion, and git's rename inference degrades
precisely when the file's frontmatter is edited in the same commit — which is
what every archive transition does. `git mv` keeps `git log --follow` and
`git blame` working across an RFC's whole life.

An RFC's implementation plan is deleted when the RFC reaches Implemented. Its
only real job is letting a later session resume half-finished work, and that job
is over; git history retains the file.

### What earns an RFC

The `brainstorming` skill already classifies every task as spike, bounded, or
architectural. That classification decides RFC-worthiness, so there is no second
judgment call to get wrong:

- **Architectural** — write an RFC.
- **Bounded** — no RFC, unless the change reverses an existing decision, in
  which case it is a supersede and needs one.
- **Spike** — no RFC. The finding becomes evidence inside the RFC it informs.

Decisions that involve no code count. Pinning an external API version, choosing
a dependency manager, or setting a repository convention are all architectural.

### How it is driven

Three mechanisms, each doing one job:

- `.claude/skills/rfc/SKILL.md` holds the procedures — numbering, transitions,
  the exact `git mv` commands, index regeneration.
- `CLAUDE.md` carries a short always-loaded rule that redirects Superpowers'
  spec output to `_rfc/` and tells sessions to read the index before design
  work. The `brainstorming` skill explicitly honors a user override of its spec
  location, so this is a supported redirect rather than a workaround.
- `_rfc/README.md` is the index a fresh session reads to orient itself.

## Alternatives considered

### Keep Superpowers' default `docs/superpowers/specs/` and add separate ADRs

Two artifacts per decision: a working spec and a short decision record pointing
at it. Rejected because the two would drift, and because it doubles the work at
exactly the moment — the end of a long design session — when a session is most
likely to skip a step. One artifact that serves both purposes is more likely to
actually get written.

### Living RFCs, amended in place

Edit the RFC and append a dated Amendments section instead of superseding.
Fewer files, one current document per topic. Rejected because the reasoning that
was overturned is the most valuable thing an RFC contains, and burying it in git
history puts it out of reach of the fresh session that most needs it.

### One directory per RFC

`_rfc/0007-slug/` containing `README.md`, `plan.md`, and research notes. Groups
everything about a decision and gives spikes somewhere to live. Rejected as
premature: at this repository's size it turns a two-paragraph decision into a
directory, and it makes `ls _rfc/` stop reading as a history.

### Archive only Superseded and Rejected, leaving Implemented at top level

Would have kept every currently-true decision in one flat listing. Rejected in
favour of the layout above, which keeps the working directory scoped to work in
flight. The cost is real and is accepted: a session must look in
`archive/implemented/` to learn how the system currently works, which is why the
index and the skill must point there prominently rather than incidentally.

### A slash command instead of a skill

`.claude/commands/rfc.md` costs nothing until invoked, but only fires when
someone remembers to type it — and the failure mode being solved here is
precisely a session not remembering. A skill's description triggers on the
situation rather than on a keystroke.

## Consequences

**Makes easy.** A fresh session orients from `_rfc/README.md` in one read.
Rejected options are recorded where they will be seen before being re-proposed.
Because Superpowers already generates approaches, trade-offs, and a review gate,
the marginal cost of an RFC over an ordinary design session is small.

**Makes hard.** Reversing a decision is deliberately more expensive than editing
a paragraph: it costs a new RFC. Finding an RFC by number requires a glob or the
index, because the number does not determine the path. The index is maintained
by hand and will drift.

**Commits us to.** Numbers are permanent and never reused. Approved bodies are
never rewritten, so a badly written RFC stays badly written until superseded.
The redirect of Superpowers' spec location is a repository-wide convention that
every future session inherits through `CLAUDE.md`.

**Deferred.** No script generates `_rfc/README.md`; the skill regenerates it by
hand. Below roughly ten RFCs the drift is cheap to correct, and a `uv` script is
weight to carry. Visible drift is the signal to write one — that would be a
bounded change, not a new RFC.

## Implementation notes
