# Tool surface, wave 1: the read half — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Register the six always-on read tools of RFC 0005's surface on top of
the existing transport, together with the three transport changes and the
`ToolError` boundary that every later wave also needs.

**Architecture:** `client.py` stays a generic HTTP chokepoint. A new `api.py`
holds one typed method per API operation, each naming its rate-limit bucket from
a single map in `buckets.py`, so no call site picks a bucket by hand. A new
`tools/` package holds the MCP tools; each is a thin translation between the
model's vocabulary and `api.py`, wrapped by one boundary that converts the
client's typed exceptions into `ToolError`. Nothing in this wave writes, polls,
chunks or exports.

**Tech Stack:** Python 3.13, `uv`, `httpx2` (**not** classic `httpx`), the MCP
Python SDK, `pytest` with `pytest-asyncio` in `asyncio_mode = "auto"`. All HTTP
is faked with `httpx2.MockTransport`. Run the suite with `uv run pytest`.

**Spec:** RFC 0013 for the tool surface, and RFC 0014 for `find_rows`' paging
and its 504 ladder. Both travel with this plan; read them before starting, and
resolve each number to its path through the index at `_rfc/README.md` rather
than guessing.

This plan was written against RFCs 0005 and 0011 and renamed when those were
superseded. **Everything it built carries forward unchanged**: 0013 keeps the
six read tools verbatim, and 0014 keeps the paging rule and the 504 ladder,
including the partial-report behaviour the task list below originally missed.
The shipped code needed no edit, because it cites topics rather than numbers —
which is what that convention is for. Read the two retired RFCs only for
history.

## Status: all eleven tasks shipped

Every task below is implemented, tested and committed. The suite stands at 195
passing. This plan stays until RFC 0005 reaches Implemented, which it has not:
this wave built the read half only, and the write surface is still gated on the
two owner decisions named at the end of this file.

**Assumption 3 is now a fact.** `GET /docs/{docId}/tables/{t}/rows/{rowId}`
returns `200`. A live read against the scratch document confirmed it, and the
endpoint inventory records both that and the more useful finding: a row's
`values` comes back keyed by **column ID**, not column name. The column cache
is therefore load-bearing for the row tools rather than an optimisation of
them. Assumptions 1 and 2 stand unratified — the bucket map is still provisional
and `find_rows`' default limit and filter shape are still invented.

**What shipped beyond this plan**, all of it required rather than elective:

- `find_rows` returns `{rows, complete, note}`, not a bare list. The
  `request-sizing` topic's 504 rule requires that rows from a pass the deadline
  cut short be kept and reported, and that the tool say how far it got. The task
  list below missed it, so as written this wave would have shipped a `find_rows`
  that violates an accepted decision.
- A refusal's detail is redacted and length-capped. It is the first server text
  this client repeats verbatim, and the existing token-leak test fired a bodyless
  `500` that never reached that path.
- The bucket map refuses to import when an operation has no bucket, rather than
  raising inside a live tool call.
- `tests/test_server.py` pins the tool surface as an exact set, widened by hand
  per task, and separately pins that every registered tool has a description.

**Six places this plan was wrong about its own repository**, corrected in the
building and worth knowing before trusting the rest of it: requests return a
response rather than a parsed body; the replay default is unsafe, so reads must
declare themselves safe explicitly; the document id is not public on the client;
the paging helper's cap was required, which would have frozen three listings at
200 items forever; `current_deadline()` does not exist, and each tool constructs
its own deadline; and the `ToolError` import path was wrong, which is fixed
above.

## Decisions this plan assumes

These are **not** settled. Each is recorded here as an assumption so that a
reviewer can reject one without re-reading the audits. If any is answered
differently, the tasks it touches change.

1. **The endpoint→bucket map in Task 4 is provisional.** RFC 0012 rule 7 is the
   only bucket assignment any RFC has ever made, and it treats the choice as
   needing an owner. This plan adopts the map on the evidence, not on authority.
   The high-stakes row is row writes → `DOC_CONTENT_WRITE`, on a staff quote that
   names `upsertRows` by name; no row write is built in this wave, so nothing
   here depends on it. Every operation this wave *does* call is a `GET`, and
   every `GET` is `READ`, which no evidence disputes.
2. **`find_rows` gets a default `limit` of 200 and a single-condition filter.**
   RFC 0005 specifies neither. 200 matches `LIST_PAGE_SIZE`; the filter shape
   follows the RFC's own statement that server-side filtering is one column and
   exact-value only.
3. **`get_row` calls `GET /docs/{docId}/tables/{t}/rows/{rowId}`.** That path
   appears in no spec excerpt in this repository; it is inferred by symmetry with
   the confirmed `PUT` on the same path. Task 10 verifies it against the live API
   before the tool is considered done.

## Global Constraints

- **Cite decisions by topic, never by number, in living documents.** This plan is
  the sole exception: it is named after one RFC and is deleted when that RFC
  reaches Implemented, so numbers here are its identity rather than a claim.
- **Never read, print, log or commit the API token.** `.env` is gitignored.
  `tests/test_client_retry.py::test_no_error_message_ever_contains_the_token`
  pins this; every new error path must keep it true.
- `TOOL_CALL_DEADLINE_S = 90.0`, of which ten seconds are reserved, leaving an
  **eighty-second working budget**. One `Deadline` per tool call is the only
  authority; nothing may extend it.
- Buckets: `READ (50, 6.0)`, `WRITE (5, 6.0)`, `DOC_CONTENT_WRITE (2, 10.0)`,
  `LIST_DOCS (2, 6.0)`. They are keyed per user, so tests never hit the network.
- `LIST_PAGE_SIZE = 200` requested and **never trusted** — the API silently
  clamps it. `LIST_PAGE_SIZE_FLOOR = 25`. `PAGE_CONTENT_LIST_LIMIT = 500`.
- `OVERVIEW_INLINE_COLUMNS_MAX_TABLES = 8`.
- Tool descriptions use the RFC's vocabulary exactly: reads that project the
  document say so; `find_rows` states that server-side filtering is one column
  and exact-value only and that everything else is applied client-side.
- Rows are addressed by ID, never by name.
- Test names are full sentences. One test file per module.

```python
def _detail_of(response: httpx2.Response) -> str:
    """Best-effort reason text. Never raises: a refusal must stay a refusal."""
    try:
        body = response.json()
    except Exception:
        return ""
    if isinstance(body, dict):
        for key in ("message", "error", "detail"):
            value = body.get(key)
            if isinstance(value, str) and value:
                return value
    return ""
```

```python
def clamp(self, candidate_s: float) -> float:
    """The lesser of a subordinate ceiling and what this deadline has left.

    A subordinate budget may consume what remains and never extend it.
    """
    return min(candidate_s, self.remaining())
```

```python
LIST_PAGE_SIZE = 200


class DocsApi:
    """One method per API operation. Buckets are resolved here, never by callers."""

    def __init__(self, client: DocsClient) -> None:
        self._client = client
        self._doc_id = client.config.doc_id

    async def _paged(self, path: str, operation: Operation,
                     deadline: Deadline, *, limit: int,
                     params: dict | None = None) -> list[dict]:
        collected: list[dict] = []
        token: str | None = None
        while len(collected) < limit:
            query = dict(params or {})
            query["limit"] = min(LIST_PAGE_SIZE, limit - len(collected))
            if token:
                query["pageToken"] = token
            body = await self._client.request(
                "GET", path, operation=operation.value,
                bucket=bucket_for(operation), deadline=deadline, params=query,
            )
            collected.extend(body.get("items", []))
            token = body.get("nextPageToken")
            if not token:
                break
        return collected[:limit]

    async def list_tables(self, deadline: Deadline) -> list[dict]:
        return await self._paged(f"/docs/{self._doc_id}/tables",
                                 Operation.LIST_TABLES, deadline, limit=LIST_PAGE_SIZE)
```

Write `list_pages`, `list_columns`, `list_page_content` and `list_rows` the same
way. `list_page_content` passes `pageContentLimit` capped at
`PAGE_CONTENT_LIST_LIMIT = 500` rather than `limit`. `get_row` is a single
unpaged request.

```python
import functools
from mcp.server.mcpserver.exceptions import ToolError
from superhumandoc_mcp.errors import ClientError


def tool_boundary(fn):
    """Translate the client's typed failures into ToolError, and nothing else.

    Only ClientError and its subclasses cross this boundary as a message the
    model sees. Anything else is a bug in this server and is left to the SDK,
    which redacts it — surfacing it verbatim would leak internals.
    """
    @functools.wraps(fn)
    async def wrapper(*args, **kwargs):
        try:
            return await fn(*args, **kwargs)
        except ClientError as failure:
            raise ToolError(str(failure)) from failure
    return wrapper
```

## What this plan deliberately does not build

Named so that a later session does not read the gap as an oversight.

- **Every write tool**, always-on and gated alike. The revisit that blocked
  them has happened: RFC 0013 decides that page content is written as HTML and
  that no tool accepts content this server produced. The write half is a new
  plan against RFC 0013, not a continuation of this one, and it waits on 0013
  being accepted.
- **Chunking and batch splitting.** Likewise unblocked by RFC 0014, which
  computes a row's size in the units the API counts rather than multiplying wire
  bytes by an estimate, and which withdraws the promise that halving ends
  holding the offending row.
- **Both poll loops and the whole export path**, and therefore `read_page`.
  A terminal status 404, and export's `410 Gone`, still have no defined outcome
  across the RFCs that touch them. This is now the only one of the original
  blockers that no decision has addressed.
- **The unauthenticated download client.** Needed only by export. When it is
  built it must be a second `httpx2.AsyncClient`: the existing one carries
  `Authorization` as a client-level default header, which is applied to every
  host it is pointed at.
- **Replay-eligibility plumbing.** RFC 0013 permits retry-after-acceptance only
  for `GET`s and for keyed upserts. Everything in this wave is a `GET`, so the
  transport's current method-based view is sufficient here and insufficient the
  moment a write lands.

# Wave 2: the write half

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Register the six always-on write tools and the six gated ones, on top
of the write calls, the mutation poll loop and the chunker they all need.

**Architecture:** `api.py` gains one method per write operation, built by its own
task rather than assumed. A new `polling.py` holds the mutation poll loop. A new
`sizing.py` computes a row's size in the units the API counts. A new
`chunking.py` splits a batch along two axes and reports every row under one of
four outcomes. `tools/writes.py` holds the tools; `tools/guard.py` holds the
pre-write check gated page operations run.

**Spec:** RFC 0013 for the tool surface and its reporting rules, RFC 0014 for
sizing and batch splitting, RFC 0012 for the mutation poll loop. Resolve each
number to its path through `_rfc/README.md`.

**This plan also implements RFC 0014**, which therefore has no plan of its own.
Splitting them would put the chunker in one file and its only callers in
another. RFC 0014 reaches Implemented when Tasks 14 and 17–18 have shipped;
RFC 0013 not until the whole surface has.

**Known defect in the spec.** RFC 0013 says *"Seventeen tools. Eleven are always
on"*. Its own enumeration gives six reads, six always-on writes and six gated —
eighteen, twelve of them always on. The body is frozen; **follow the
enumeration, not the count.**

Seventeen of the eighteen are built here. `read_page` is deferred with the
export flow (assumption 8), and `replace_element` is conditional on Task 12 —
if the probe shows the API cannot scope a write to one element, that tool is
not built and the wave ships sixteen. Neither is an omission: both are

## Global Constraints

Wave 1's Global Constraints still hold. Additionally:

- **Page content is HTML.** `canvasContent.format` is `html` on every
  page-content write. Never markdown.
- **No tool accepts content this server produced.** Every write tool's
  description says so, and Task 21 pins that with a test — it is the only
  enforcement there is, because `content` is a free string and no code can tell
  where a caller got it.
- **Writes report *applied*, never *succeeded*.**
- **An unknown outcome says three things**: that it is unknown, that the write
  is queued and not confirmed, and **that it may already have been applied**.
  The third is not decoration — `failure-policy` added it because *"'unknown'
  alone invites a user to retry by hand and duplicate rows"*, and this API has
  no idempotency keys. `OutcomeUnknown` already carries that sentence for the
  transport case; the poll loop must not say less about the same risk.
- **`warning` is absent, not null.** Read with `.get`, surface verbatim.
- **Rows are addressed by ID, never by name**, for updates and deletes alike.
- **Replay after transmission is permitted only for `GET`s and for upserts with
  `key_columns` set.** A 429 carries no such restriction.
- `MUTATION_INITIAL_SLEEP_S 3.0`, `MUTATION_POLL_INTERVAL_S 2.0`,
  `MUTATION_POLL_BACKOFF ×1.5` to `MUTATION_POLL_MAX_INTERVAL_S 15.0`,
  `MUTATION_404_GRACE_S 30.0`, `MUTATION_DEADLINE_S 60.0`.
- `MAX_ROW_INTERNAL_BYTES 84_000`, `MAX_REQUEST_BYTES 1_500_000`,
  `MAX_ROWS_PER_UPSERT 100`, `MAX_ROW_IDS_PER_DELETE 500`,
  `MAX_PAGE_CONTENT_BYTES 700_000`, `CHUNK_COST_ESTIMATE_S 30.0`.
- The mutation status endpoint is at the **root**: `GET
  /mutationStatus/{requestId}`, *not* under `/docs/{docId}/`. Every existing
  `DocsApi` method interpolates a doc id; this is the first that must not, so
  do not copy the pattern blindly.
- **No new `Operation` members are needed.** `Operation` is keyed by API
  operation, not by tool: `replace_element` and `overwrite_page` both use
  `updatePage`, and `delete_element` uses `deletePageContent`, which takes
  element IDs. `buckets.py` raises at import if a member has no bucket, so
  adding spurious members breaks the package rather than failing a test.
- **The column cache needs no invalidation in this wave.** `schema_cache.py`
  warns that the first wave to write must invalidate it and cannot key that on
  `updatedAt`. Nothing here changes a column schema — the API has no column
  creation at all — so the warning is discharged by scope, not ignored. A wave
  that adds a schema-changing write inherits it.

## Decisions this wave assumes

Wave 1's three assumptions still stand, and **assumption 1 now matters**: every
row write here is charged to `DOC_CONTENT_WRITE` on a map no RFC has ratified.
Wave 1 was all `GET`s. If the map is wrong the tools still work — chunks are
sent sequentially with a poll of tens of seconds between them, so neither
bucket's window ever binds — but `tests/test_buckets.py` tests the code against
itself and would not notice.

4. **A terminal mutation-status 404 reports the outcome as unknown, never a
   failure.** Rule 3 makes it terminal and names no outcome. The write was
   accepted with a 202, so asserting failure would state what no evidence
   supports.
5. **A 5xx or 429 that survives the transport's own retries mid-poll reports
   the same unknown outcome**, rather than escaping as a raw error. The write
   was accepted; losing sight of it is not the same as it failing, and a bare
   error would read to a model as though nothing had happened.
6. **A `202` carrying no `requestId` reports unknown too.** `failure-policy`
   records that some 202s carry none. There is then nothing to poll, and the
   write may still apply. Left unhandled this surfaces as a `KeyError`, which
   the tool boundary deliberately does *not* translate, so a model would see
   "Error executing tool" for a write that may have succeeded.
7. **A warning on a chunked write is reported per chunk, against the rows that
   chunk carried**, not collapsed into one field. Collapsing would attribute a
   warning about rows 1–100 to rows 101–200 as well.
8. **Export stays out of scope**, so `410 Gone` is never reached and `read_page`
   is not built. It is the last always-on tool with no implementation.

Assumptions 4 through 7 all close gaps in `async-operations`, whose RFC is
frozen. They are listed so a reviewer can reject one without reading the tasks.

```python
import json

MAX_ROW_INTERNAL_BYTES = 84_000
MAX_REQUEST_BYTES = 1_500_000


def row_internal_bytes(values: dict) -> int:
    """A row's size as the API counts it: UTF-8 length, newlines charged twice.

    Fitted to nine samples across Latin text, CJK, emoji and newline-dense
    content to about 1%. Computed, not estimated — the inflation factor this
    replaced sat above a ratio that provably cannot exceed 2.0.
    """
    total = 0
    for value in values.values():
        text = value if isinstance(value, str) else str(value)
        total += len(text.encode("utf-8")) + text.count("\n")
    return total


def request_wire_bytes(payload: object) -> int:
    """Bytes actually put on the wire — a different axis, a different unit,
    guarding a different limit."""
    return len(json.dumps(payload, ensure_ascii=False).encode("utf-8"))
```

### Task 15: The mutation poll loop

**Files:** Create `src/superhumandoc_mcp/polling.py`. Test: `tests/test_polling.py`.

**Interfaces:**
- Consumes: `DocsApi.get_mutation_status` (Task 13), `Deadline.clamp`,
  `Deadline.can_afford`, `UpstreamRefused.status`.
- Produces: `MutationOutcome(applied: bool, warning: str | None, detail: str)`
  and `await await_mutation(api, request_id, deadline, *, clock, sleep)`.

One bounded loop. Wait `MUTATION_INITIAL_SLEEP_S`, then poll at
`MUTATION_POLL_INTERVAL_S` backing off by `MUTATION_POLL_BACKOFF` to
`MUTATION_POLL_MAX_INTERVAL_S`, until `completed: true`, or
`deadline.clamp(MUTATION_DEADLINE_S)`, whichever comes first.

**The 404 is caught inside this loop**, around each `get_mutation_status` call —
never by special-casing the mutation-status path inside the transport's
classifier. That classifier is a frozen, uniform table with no per-endpoint
carve-out, and the reconciliation belongs to the loop: a poll is not a retry,
and nothing here weakens the replay rules.

**Every non-applied outcome says all three things** — unknown, queued and not
confirmed, and may already have been applied. Write the sentence once, as a
module constant, so the three exit paths cannot drift apart.

```python
UNKNOWN = (
    "The outcome is unknown: the write was queued and not confirmed before "
    "this call ran out of time. It may already have been applied — check "
    "before sending it again, because this API has no idempotency keys and a "
    "repeat may duplicate it."
)


async def await_mutation(api, request_id, deadline, *, clock, sleep):
    """Poll one mutation to completion, or to a bounded give-up.

    The operation's own ceiling never extends the tool call's: `clamp` takes
    the lesser. A 404 is caught here rather than in the transport, whose
    classification table is uniform and has no per-endpoint carve-out.
    """
    started = clock()
    ceiling = started + deadline.clamp(MUTATION_DEADLINE_S)
    grace_ends = started + MUTATION_404_GRACE_S
    interval = MUTATION_POLL_INTERVAL_S
    await sleep(MUTATION_INITIAL_SLEEP_S)
    while clock() < ceiling and deadline.can_afford(interval):
        try:
            body = await api.get_mutation_status(request_id, deadline)
        except UpstreamRefused as refusal:
            if refusal.status == 404 and clock() < grace_ends:
                pass                     # not yet: the status has not replicated
            else:
                return MutationOutcome(False, None, UNKNOWN)
        except ClientError:
            return MutationOutcome(False, None, UNKNOWN)
        else:
            if body.get("completed"):
                return MutationOutcome(True, body.get("warning"), "applied")
        await sleep(interval)
        interval = min(interval * MUTATION_POLL_BACKOFF, MUTATION_POLL_MAX_INTERVAL_S)
    return MutationOutcome(False, None, UNKNOWN)
```

### Task 18: The chunker

**Files:** Create `src/superhumandoc_mcp/chunking.py`. Test: `tests/test_chunking.py`.

**Interfaces:**
- Consumes: `row_internal_bytes`, `request_wire_bytes`, `BatchReport`,
  `RowOutcome`, `Deadline`, `ThrottleRefused`, `UpstreamRefused`.
- Produces:
  `plan_chunks(rows, *, max_rows, max_row_bytes, max_request_bytes) -> list[list[int]]`
  returning **indices into the caller's list**, and
  `await send_chunks(chunks, rows, send, deadline, *, report) -> BatchReport`,
  where `send(subset_indices) -> MutationOutcome` performs one write and polls
  it.

`plan_chunks` returns indices rather than rows so that every outcome can be
attributed to the caller's original position, which is what makes the suffix
property expressible at all.

**Chunks are sent strictly in order**, and the moment one is not started every
remaining chunk is marked not attempted without being tried. That ordering is
what makes the not-attempted rows a suffix; it is not an optimisation.

**`CHUNK_COST_ESTIMATE_S` is an admission gate, not a bound.** A chunk admitted
on a 30-second estimate may legitimately take up to `MUTATION_DEADLINE_S`, which
is 60 — twice the estimate. So one slow chunk can consume a budget the gate
believed it was spending a third of, and the rest are reported not attempted.
That is correct behaviour rather than a defect, but it must be pinned, because
the obvious reading of the estimate is that it bounds the cost.

## What this wave still does not build

- **`read_page`, the export flow and its poll loop.** The last always-on tool
  with no implementation. Blocked on export's own gaps: `410 Gone` has no
  defined outcome, `EXPORT_DEADLINE_S` is inert at its current value,
  re-minting a download link happens inside a tail reserved on the grounds that
  nothing like it happens there, and there is no unauthenticated client for the
  download hop. Those need a decision on `async-operations`, whose RFC is frozen.
- **A second `httpx2.AsyncClient` for the download host**, and lifecycle
  management for either. The existing one carries `Authorization` as a
  client-level default header applied to every host it is pointed at, so the
  download hop cannot reuse it. Nothing closes either client today.
- **Concurrent mutations.** RFC 0014 declined to decide this and it belongs to
  `async-operations`. Everything here is sequential, which is also what makes
  the not-attempted rows a suffix.
